# 参考文献梳理标签页规划

## 1. 背景

当前系统已经具备若干和“参考文献梳理”相关的基础能力，但它们仍然是分散的：

- 可以对 PDF 做文本抽取与分段；
- 可以从分段后的内容中识别参考文献区；
- 可以调用 DeepSeek 将参考文献目录解析成结构化条目；
- 可以对正文中的引用候选段进行追踪与核验；
- 可以将文献元数据存入 `bib_entries`，并在“我的文献库”中展示。

但这些能力尚未被整合成一个正式的、多用户可视化功能：

- 没有独立标签页；
- 没有任务化执行入口；
- 没有数据库中的“被引关系 / 引用文本”实体层；
- 没有将“参考文献目录解析结果”和“正文引用命中结果”统一回写到文献库；
- 没有把“源文献 → 被引文献”的关系显式存储下来。

你希望新增一个大功能：

1. 对每一篇上传的 PDF 文档做参考文献梳理；
2. 充分利用 DeepSeek 的上下文缓存，稳定抽取参考文献目录；
3. 把参考文献条目和正文中的引用文本对应起来；
4. 用表格形式可视化；
5. 从参考文献目录中析出题录信息并入库到“我的文献库”；
6. 同时存好“谁引用了谁”的引用关系；
7. 在数据库里保存具体的引用文本。

本文件用于形成一份可直接指导后续实施的详细规划。

> 说明：本文档已经吸收 `REFERENCE_CITATION_DEEPSEEK_FLASH_PLAN.md` 的新识别方案。  
> 后续若无特殊说明，应以本文档作为 `P0` 参考文献梳理功能的主规划文档；`REFERENCE_CITATION_DEEPSEEK_FLASH_PLAN.md` 作为专项补充说明保留。

## 1.1 当前识别方案调整结论

本规划当前已明确调整参考文献识别策略，不再继续以“纯规则拆分”为主，而改为：

- **程序负责定位参考文献候选范围**
- **DeepSeek `deepseek-v4-flash` 负责语义判断、分条和结构化**

这次调整的直接原因是，实际试运行中已经暴露出以下问题：

- 标题识别不稳定；
- 错误断行较多；
- 文末英文摘要、附录、补充材料容易被误判为参考文献；
- 纯规则对复杂版式和中英文混排的适应性不足。

因此，本文档后续所有涉及“参考文献目录提取”的部分，都应按“规则辅助、模型主导”的新方案理解。

## 2. 目标

本功能的最终目标不是“再做一个抽取脚本”，而是新增一个完整的产品能力层：

### 2.1 用户目标

- 对当前用户上传的任意一篇 PDF，执行“参考文献梳理”。
- 在页面中看到：
  - 文末参考文献目录；
  - 每条参考文献的结构化题录；
  - 是否已经匹配到当前文献库中的现有文献；
  - 正文里哪些位置引用了它；
  - 这些引用的原始文本/上下文。
- 将未入库的参考文献一键导入“我的文献库”。
- 在文献库中看到明确的：
  - 谁引用了谁；
  - 某篇文章引用了哪些文献；
  - 某篇文章被当前库中的哪些文献引用。

### 2.2 系统目标

- 把“参考文献抽取”和“正文引用追踪”正式纳入多用户任务体系。
- 将结果结构化入库，而不再停留在脚本产物。
- 保留 Excel / Markdown 产物，方便下载与审计。
- 为后续做引用网络、共引分析、文献追踪打好数据库基础。

## 3. 术语定义

为了避免后续实现时混淆，先统一几个概念：

### 3.1 源文献

- 指当前正在处理的那篇 PDF。
- 在数据库中通常对应一个 `bib_entries` 记录。

### 3.2 参考文献条目

- 指源文献文末参考文献目录中的某一条。
- 它是“被源文献引用的对象”。

### 3.3 被引文献

- 指参考文献条目所指向的真实文献。
- 它可能：
  - 已存在于当前用户的文献库；
  - 不存在，需要新建 `bib_entries`；
  - 暂时无法可靠匹配，只能保留为原始参考文献条目。

### 3.4 正文引用命中

- 指源文献正文中的某一段、某一句、某个括号引用，与某条参考文献条目发生对应关系。

### 3.5 引用文本

- 指正文中与某条参考文献对应的原始文本片段、上下文片段或归一化命中文本。

## 4. 当前可复用基础

目前仓库中已经有若干可以直接复用的基础模块：

### 4.1 参考文献区抽取

- `extract_references.py`
  - 已具备从 `*_segmented.md` 中截取参考文献区、并用 LLM 解析结构化字段的能力。
- 当前 `P0` 已有实现中也已经具备：
  - 参考文献任务入口；
  - `bib_references` / `bib_reference_citations` 入库骨架；
  - 前端标签页与结果表格基础。

当前判断：

- 这些基础能力可以继续复用；
- 但“如何把文末文本稳定识别成参考文献条目”这一环，需要从旧的启发式拆分逻辑，切换到 `DeepSeek v4 flash` 主导的新方案。

### 4.2 正文引用追踪

- `citation_tracer.py`
  - 已具备正文预处理、候选召回、LLM 核验和上下文摘录能力。

### 4.3 DeepSeek 长上下文缓存

- `new_architecture/paper_cache.py`
- `new_architecture/conversation_engine.py`

这些模块已经证明：

- 可以用稳定前缀提升 DeepSeek prompt cache 命中；
- 可以在围绕同一篇文档做多轮调用时降低重复成本；
- 适合迁移到“参考文献梳理”这一新功能中。

当前进一步判断：

- 新上传 PDF 场景应优先复用这套上下文缓存能力；
- 已有 PDF 场景则以“尾部参考文献候选区 + 稳定 Prompt 前缀”的轻量缓存为主。

### 4.4 文献库与数据库基础

- 当前已有 `bib_entries` 作为文献档案枢纽；
- 当前已有 `jobs` / `job_bib_entries` / `artifacts` 用于任务与产物挂载；
- 当前已有“我的文献库”页面与 API，可作为新功能的承接点。

## 5. 功能范围

## 5.1 本期目标范围

本期规划建议覆盖：

1. 新增独立标签页；
2. 以“源 PDF”为入口执行参考文献梳理任务；
3. 从 PDF 中抽取参考文献目录并解析成结构化条目；
4. 从正文中识别引用命中并和参考文献条目对齐；
5. 结果以表格形式展示；
6. 解析后的参考文献题录可入库到“我的文献库”；
7. 数据库保存：
   - 参考文献条目；
   - 引用关系；
   - 具体引用文本；
   - 任务产物。

## 5.2 暂不纳入本期范围

首期不建议同时做太多图谱型功能：

- 不先做复杂引用网络可视化图谱；
- 不先做跨用户的全库被引统计；
- 不先做共被引 / 共引分析；
- 不先做跨文档批量图分析；
- 不先做图数据库接入。

这些内容应建立在首期结构化数据稳定后再扩展。

## 6. 产品形态规划

### 6.1 新增标签页

建议新增一个工作台标签页：

- `参考文献梳理`

推荐位置：

- 放在 `我的文献库` 附近或其前后
- 因为它和文献资产管理是同一类认知任务

推荐顺序可后续再定，但建议属于“管理/分析增强页”，不应塞进已有精读/对比标签内部。

### 6.2 页面定位

该标签页本质上是：

- 面向单篇源文献的“引用解析工作台”

而不是：

- 普通上传页
- 简单历史页
- 只读结果页

### 6.3 页面核心区域

建议页面分成 4 块：

1. **源文献选择区**
   - 从当前用户已有 PDF 文献中选择一篇；
   - 支持显示标题、作者、年份、是否已梳理。

2. **任务控制区**
   - `开始梳理`
   - `重新梳理`
   - `仅重跑引用追踪`
   - `导出 Excel`
   - `导出 Markdown`

3. **结果总览区**
   - 参考文献总数
   - 已匹配到文献库的数量
   - 新导入数量
   - 正文引用命中总数
   - 未匹配条目数量

4. **明细表格区**
   - 参考文献条目
   - 结构化题录
   - 文献库匹配状态
   - 正文命中次数
   - 引用文本预览
   - 操作按钮

### 6.4 明细表格建议列

首版建议包含以下列：

- 序号
- 参考文献原文
- 解析标题
- 作者
- 年份
- 期刊 / 出版源
- DOI
- 文献库状态
  - 已匹配
  - 已新建
  - 未匹配
- 对应文献库记录
- 正文命中次数
- 引用文本预览
- 操作
  - 查看引用
  - 重新匹配
  - 导入文献库

### 6.5 引用文本查看方式

建议不要把所有引用文本直接塞进表格列里，会很乱。

推荐方案：

- 表格里只显示：
  - `命中 3 次`
  - `查看`
- 点击后右侧抽屉或下方展开详情：
  - 每次命中的引用文本
  - 所在段落上下文
  - 页码 / 段号 / 小节（如果能识别）
  - 置信度

## 7. 任务流程规划

推荐把整条链路正式变成任务化流程：

### 7.1 阶段 A：源文献准备

输入：

- 当前用户选择的一篇源 PDF

处理：

- 校验当前用户权限
- 找到对应 `file_id`
- 找到或创建对应 `source_bib_entry_id`
- 准备文档工作区

输出：

- 源文献上下文对象
- 引用梳理任务记录

### 7.2 阶段 B：文本抽取与分段

输入：

- 源 PDF

处理：

- 若已有可靠的分段 Markdown 产物，则优先复用；
- 若没有，则复用当前 PDF → Markdown / segmented 流程；
- 在这里开始区分两种场景：
  - `新上传 PDF 精读场景`
    - 复用精读链路已提取的全文文本、分段结果和文档上下文；
    - 在精读过程中顺带准备参考文献候选区；
  - `已有 PDF 文档场景`
    - 不重新跑整篇精读；
    - 只读取尾部若干页或全文尾部区段，准备参考文献候选区；
- 为后续两条链路准备两份数据：
  - 文末参考文献候选区；
  - 正文（去掉参考文献区后的主体）。

输出：

- `segmented_md`
- `body_text`
- `references_section_text`

### 7.3 阶段 C：参考文献目录提取

输入：

- `references_section_text`

处理：

- 本阶段不再以“纯规则拆分”为主，而采用两段式方案：
  1. 程序先定位候选范围；
  2. 再调用 `DeepSeek deepseek-v4-flash` 做语义判断、分条和结构化。
- 候选范围定位时：
  - 优先寻找 `References / Bibliography / Works Cited / 参考文献` 等标题；
  - 从该位置向后截取候选文本；
  - 对已有 PDF 场景，优先只处理尾部相关页或尾部区段；
  - 对新上传 PDF 场景，优先复用精读链路中的文本与上下文。
- 在 Prompt 中必须强调：
  - 文末后续可能还有英文摘要、附录、补充材料、致谢、作者简介等内容；
  - 这些内容不是参考文献，必须忽略；
  - 不得把普通段落或摘要段落当作题录。
- 调用 DeepSeek 时统一采用：
  - `base_url = https://api.deepseek.com`
  - `model = deepseek-v4-flash`
- 返回结果要求为严格 JSON，并至少包含：
  - `raw_text`
  - `authors`
  - `year`
  - `title`
  - `journal`
  - `volume`
  - `issue`
  - `pages`
  - `doi`
  - `language`
  - `ignore`
  - `ignore_reason`

当前不建议：

- 不建议继续使用旧模型名 `deepseek-chat` 或 `deepseek-reasoner` 作为正式配置名；
- 不建议把整篇 PDF 文本直接无差别送给模型；
- 不建议继续以正则和启发式规则承担主要分条职责。

输出：

- 结构化参考文献条目列表

### 7.4 阶段 D：参考文献条目归一化

输入：

- 结构化参考文献条目列表

处理：

- 过滤模型返回的 `ignore = true` 条目；
- 规范作者列表；
- 规范年份；
- 规范标题；
- 规范 DOI；
- 清洗明显异常值；
- 生成 `reference_dedup_key`

输出：

- 可入库的规范化参考文献条目

### 7.5 阶段 E：文献库匹配 / 导入

输入：

- 规范化参考文献条目
- 当前用户已有 `bib_entries`

处理：

- 先按 DOI 精确匹配
- 再按标题 / 作者 / 年份相似度匹配
- 若命中已有文献库：
  - 建立引用关系
- 若未命中：
  - 先保留为参考文献条目
  - 可由用户一键导入文献库
  - 或按高置信度自动入库

输出：

- `matched_bib_entry_id`
- `newly_created_bib_entry_id`
- `unmatched` 状态

### 7.6 阶段 F：正文引用候选召回

输入：

- `body_text`
- 规范化参考文献条目

处理：

- 为每条参考文献生成引用指纹：
  - 数字编号型
  - 作者-年份型
  - 标题关键词型
- 在正文中召回候选引用段

输出：

- 每条参考文献的候选段列表

### 7.7 阶段 G：LLM 引用核验

输入：

- 候选段列表
- 参考文献条目元数据

处理：

- 调用 DeepSeek 判断：
  - 该候选段是否真的在引用该条参考文献
  - 具体引用文本是什么
  - 最佳上下文摘录是什么
  - 置信度如何

输出：

- 命中清单
- 引用文本
- 上下文摘录
- 置信度

### 7.8 阶段 H：结果入库

输入：

- 参考文献条目
- 匹配结果
- 正文引用命中

处理：

- 保存参考文献条目
- 保存引用关系
- 保存具体引用文本
- 生成 Excel / Markdown 产物
- 记录 `jobs` 与 `artifacts`

输出：

- 页面可查询的结构化数据
- 可下载产物

## 8. DeepSeek 上下文缓存策略

这是本功能的关键优化点之一。

### 8.1 为什么需要缓存

参考文献梳理不是一次 LLM 调用，而是一个多阶段任务：

- 解析参考文献目录
- 结构化提取
- 引用核验
- 可能还有补充元数据识别

如果每一步都重新发送大量相同文本，会：

- 成本高
- 速度慢
- 结果不稳定

### 8.2 推荐缓存策略

以“同一篇源文献”为核心建立稳定上下文。

建议分两层：

#### 文档级上下文

- 文档基础元数据
- 预处理后的正文文本
- 参考文献区文本
- 固定系统前缀

这部分尽量保持不变，用于提升 prompt cache 命中。

#### 阶段级子上下文

- 某一批参考文献条目块
- 某一批候选引用段

这部分随任务阶段变化，但保持稳定的拼接格式。

同时明确区分两种使用方式：

- `新上传 PDF 精读场景`
  - 优先复用精读链路已经建立的文档级上下文；
  - 这是上下文缓存收益最大的场景。
- `已有 PDF 文档场景`
  - 不强依赖完整精读上下文；
  - 以尾部候选区文本缓存、稳定 Prompt 前缀和局部重试缓存为主。

### 8.3 推荐实现方式

建议复用现有 `PaperCache` / `ConversationEngine` 思路，但不要直接把它硬塞进当前精读逻辑。

更合理的做法是新增：

- `ReferenceTraceCache`

职责：

- 为同一 `file_id` 缓存预处理文本
- 为同一任务生成稳定 prompt 前缀
- 统计 `prompt_cache_hit_tokens`
- 给多个 extraction / verification 调用复用

### 8.4 哪些阶段最值得吃缓存

优先收益最大的是：

1. 参考文献目录结构化解析（尤其是 `deepseek-v4-flash` 的多轮局部解析）
2. 正文引用命中核验

原因：

- 这两阶段都要多次围绕同一份源文本调用模型
- 非常适合复用稳定前缀

## 9. 数据库设计规划

当前不建议把这些数据塞进已有表中。

推荐新增独立表。

### 9.1 新表：`bib_references`

作用：

- 存储“某篇源文献的参考文献条目”

建议字段：

- `id`
- `owner_user_id`
- `source_bib_entry_id`
- `source_job_id`
- `reference_order`
- `raw_text`
- `authors_json`
- `year`
- `title`
- `journal`
- `volume`
- `issue`
- `pages`
- `doi`
- `language`
- `dedup_key`
- `matched_bib_entry_id`
- `match_method`
- `match_score`
- `citation_count`
- `created_at`
- `updated_at`

字段语义：

- `source_bib_entry_id`
  - 这条参考文献属于哪篇源文献
- `matched_bib_entry_id`
  - 这条参考文献是否已对应到文献库中的某篇文献

  - 在正文中命中的次数

### 9.2 新表：`bib_reference_citations`

作用：

- `source_job_id`
- `citation_index`
- `page_label`
- `section_label`
- `paragraph_label`

这里的关键就是你明确要求要进数据库的：

建议至少存：

## 10. 文献库入库与引用关系策略

### 10.1 参考文献条目是否全部变成 `bib_entries`

不建议一上来自动把所有参考文献条目都变成正式文献库记录。

原因：

- 参考文献解析结果可能不完整；
- 会把大量脏数据直接灌入文献库；
- 有些条目可能只是书籍、报告、政策文件，不一定要立即变成正式文献档案。

### 10.2 推荐策略

分三层：

1. **先保存到 `bib_references`**
   - 任何解析出的参考文献都先进入这里

2. **若高置信度匹配到已有 `bib_entries`**
   - 直接建立关系

3. **若未匹配**
   - 用户可一键导入到文献库
   - 或系统只在高置信度时自动新建

### 10.3 引用关系如何表示

通过 `bib_references` 本身即可表达边：

- `source_bib_entry_id` = 源文献
- `matched_bib_entry_id` = 被引文献

当 `matched_bib_entry_id` 不为空时，说明：

- 当前源文献引用了当前文献库中的这篇被引文献

## 13. 后端服务拆分规划

建议拆成以下服务，而不是把所有逻辑塞进一个 router：

### 13.1 `reference_extract_service`

- 找参考文献候选区；

### 13.3 `citation_trace_service`

### 13.4 `reference_import_service`

### 13.5 `reference_cache_service`

职责：

- 管理基于 DeepSeek 的稳定上下文缓存

- 统计 cache hit 情况

  - 新上传 PDF 的精读链路缓存复用；
  - 已有 PDF 的尾部候选区轻量缓存。

## 15. 风险点

### 15.1 PDF 版式风险

- 参考文献区可能断页
- 双栏排版可能干扰顺序
- 页眉页脚可能污染条目

### 15.2 引用风格风险

- 数字编号制
- 作者-年份制
- 中文“某某（2020）”式写法
- 一条参考文献多次命中

### 15.3 LLM 稳定性风险

- 分块过大可能超上下文；
- 分块过小可能切断条目；
- 模型可能返回不稳定 JSON；
- 模型可能把英文摘要、附录误当题录；
- 引用核验若候选太多可能漏掉。

### 15.4 数据污染风险

- 低质量参考文献条目误导入文献库
- 错误匹配导致源文献与被引文献关系错误

因此首期应偏保守：

- 先保存参考文献条目
- 再做高置信度匹配
- 对低置信度匹配保留人工确认
- 对模型不确定字段允许 `null`，不要强填
- 对 `ignore=true` 条目不入库为正式参考文献
