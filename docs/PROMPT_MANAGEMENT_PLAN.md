# 提示词管理改造方案

## 1. 背景

当前仓库中的“提示词管理”已经有一个可用的前后端入口，但它本质上还是一个基于文件系统的简单编辑器，而不是面向多用户系统的正式配置中心。

现状包括：

- 前端提示词管理页通过 `GET /api/prompts` 和 `PUT /api/prompts` 直接读取、修改 `prompts/` 目录下的 Markdown 文件。
- 后端没有独立的提示词数据库表。
- 多用户规划文档中目前仍写的是“提示词全局共享（不按用户隔离）”。
- 当前页面会出现“内容为空”的情况，且用户很难区分这是因为：
  - 还没有加载；
  - 对应文件不存在；
  - 当前类型/步骤没有默认值；
  - 长文本提示词实际运行链路没有正确命中管理页对应文件。

这套方案在单机单用户阶段可以工作，但已经不适合当前的多用户化目标。

## 2. 当前问题

### 2.1 存储层问题

- 提示词没有进入数据库。
- 系统默认值依赖仓库中的文件存在。
- 无法区分“系统默认提示词”和“某个用户自己的提示词”。
- 缺少审计、版本、更新时间、修改人等元数据。

### 2.2 多用户问题

- 当前提示词是全局共享的，任何修改都会影响所有用户。
- 无法支持“每个用户根据自己的研究偏好调整提示词”。
- 无法支持“管理员维护系统默认提示词，普通用户基于默认提示词做个人覆盖”。

### 2.3 运行链路问题

- `quant / qual / filter / long` 的提示词读取分散在不同模块中。
- 长文本精读链路与管理页的提示词来源不完全统一，存在路径与兜底逻辑不一致的问题。
- 即使前端页面改了某些提示词，也未必能保证实际运行时命中的就是该内容。

### 2.4 前端体验问题

- 页面默认不自动加载。
- 后端返回 `exists=false` 时，前端仍可能表现为空白而没有清晰解释。
- 缺少“当前生效来源”展示，用户不知道自己看到的是：
  - 系统默认；
  - 个人覆盖；
  - 文件兜底；
  - 空内容。

## 3. 改造目标

本次改造目标如下：

1. 将当前默认提示词纳入数据库管理。
2. 支持系统默认提示词与用户个人提示词覆盖。
3. 统一所有分析链路的提示词读取方式。
4. 前端提示词管理页面能够明确展示当前来源与可操作范围。
5. 保持兼容性，在迁移过程中避免因缺失数据导致业务链路中断。

## 4. 核心设计原则

### 4.1 系统默认 + 用户覆盖

推荐采用以下模型：

- 系统默认提示词：
  - 由管理员维护；
  - 面向所有用户共享；
  - 作为用户未自定义时的默认来源。
- 用户个人提示词：
  - 仅对当前用户生效；
  - 作为系统默认提示词之上的覆盖层；
  - 删除覆盖后自动恢复为系统默认。

### 4.2 固定槽位，不开放自由命名

当前阶段不建议允许用户随意新增任意 `type/key`，而是继续沿用现有固定槽位：

- `quant.step_1` ~ `quant.step_7`
- `qual.L1` ~ `qual.L4`
- `long.overview` ~ `long.custom`
- `filter.explorer` / `filter.reviewer` / `filter.empiricist`

这样可以降低复杂度，避免运行链路和管理配置脱节。

### 4.3 运行时解析必须统一

所有业务链路统一通过同一个 `PromptService` 获取提示词，不再各模块直接读文件。

统一优先级建议：

1. 当前用户的个人覆盖
2. 系统默认提示词
3. 仓库文件兜底
4. 代码内置兜底文案

## 5. 数据库设计

## 5.1 新表建议

建议新增表：`prompt_templates`

### 字段建议

- `id`
- `owner_user_id`
- `scope`
- `prompt_type`
- `prompt_key`
- `title`
- `content`
- `created_at`
- `updated_at`
- `updated_by_user_id`

### 字段语义

- `owner_user_id`
  - `NULL` 表示系统默认提示词
  - 非 `NULL` 表示该用户自己的覆盖提示词
- `scope`
  - 建议取值：`system` / `user`
- `prompt_type`
  - 如：`quant` / `qual` / `long` / `filter`
- `prompt_key`
  - 如：`step_1` / `L1` / `overview` / `explorer`
- `title`
  - 用于前端展示的人类可读名称
- `content`
  - 提示词正文
- `updated_by_user_id`
  - 记录最后一次修改该记录的用户

### 约束建议

- 唯一约束：`(owner_user_id, prompt_type, prompt_key)`
- 对系统默认值，业务层保证每个 `prompt_type + prompt_key` 仅有一条有效记录

## 5.2 为什么不继续用 `user_settings.preferences_json`

虽然当前库里已有 `user_settings.preferences_json` 预留字段，但不建议把提示词直接塞进去，原因如下：

- 提示词是结构化配置，不适合长期放在大 JSON 中。
- 后续需要单独查询、回退、权限校验、审计和测试。
- 单独成表后更利于维护、迁移和扩展。

因此，建议使用独立表，不复用 `user_settings.preferences_json`。

## 6. 默认提示词入库方案

## 6.1 默认值来源

首批系统默认提示词来自当前仓库中的文件：

- `prompts/quant_analysis/*.md`
- `prompts/qual_analysis/*.md`
- `prompts/long/*.md`
- `prompts/literature_filter/*.md`

## 6.2 初始化策略

建议新增一个幂等的初始化逻辑，例如：

- 启动时执行一次“补齐缺失系统默认值”
- 或提供单独脚本执行

逻辑原则：

- 如果数据库中该系统默认槽位不存在，则从文件导入。
- 如果数据库中已经存在系统默认值，则不覆盖。

这样可以保证：

- 首次升级后数据库中立即有完整默认提示词。
- 后续系统默认值以数据库为主，不会被文件意外覆盖。

## 6.3 文件的后续定位

迁移完成后，`prompts/` 目录不再作为主存储，仅作为：

- 初始化来源；
- 迁移兜底；
- 极端情况下的最后回退来源。

## 7. 后端服务设计

## 7.1 PromptService

建议新增统一服务层，例如 `PromptService`，负责：

- 读取当前用户的生效提示词
- 查询系统默认提示词
- 查询用户个人覆盖
- 保存用户个人覆盖
- 保存系统默认提示词
- 删除用户个人覆盖
- 批量返回所有槽位及其来源状态

## 7.2 统一调用点

以下模块都改为只通过 `PromptService` 获取提示词：

- 文献筛选
- 七步精读
- 四步精读
- 长文本精读
- 提示词管理接口

这样可以彻底消除当前“不同模块各读各的来源”的问题。

## 8. API 设计

## 8.1 面向普通用户

### `GET /api/prompts/catalog`

作用：

- 返回所有可管理的提示词槽位
- 返回每个槽位的：
  - 类型
  - key
  - 标题
  - 是否存在系统默认
  - 是否存在个人覆盖
  - 当前生效来源

### `GET /api/prompts/item?type=&key=`

作用：

- 获取某个提示词槽位的完整信息

建议返回：

- `type`
- `key`
- `title`
- `effective_content`
- `system_content`
- `user_content`
- `source`

### `PUT /api/prompts/my`

作用：

- 保存当前用户的个人覆盖提示词

### `DELETE /api/prompts/my?type=&key=`

作用：

- 删除当前用户对该槽位的覆盖
- 删除后恢复使用系统默认提示词

## 8.2 面向管理员

### `PUT /api/prompts/system`

作用：

- 修改系统默认提示词

### 可选：`POST /api/prompts/seed`

作用：

- 手动补齐缺失的系统默认提示词

## 8.3 权限规则

- 所有已登录用户：
  - 可以查看提示词目录
  - 可以查看当前生效内容
  - 可以修改自己的个人覆盖
- 仅管理员：
  - 可以修改系统默认提示词
  - 可以执行默认值补齐或系统级管理动作

## 9. 前端页面改造方案

## 9.1 页面目标

前端提示词管理页应从“文件编辑器”升级为“提示词中心”。

## 9.2 最小可用交互

建议页面包含以下信息：

- 提示词类型选择
- 步骤/槽位选择
- 当前来源标识：
  - 系统默认
  - 个人覆盖
- 当前生效内容
- 我的个人覆盖编辑区
- 恢复默认按钮

管理员额外可见：

- 系统默认内容编辑区
- 保存系统默认按钮

## 9.3 交互建议

- 切换类型或步骤时自动加载
- 明确显示：
  - 当前生效来源
  - 是否已有个人覆盖
  - 系统默认是否存在
- 保存个人覆盖后立即刷新当前状态
- 删除个人覆盖后立即回退为系统默认

## 9.4 为什么不建议继续只保留一个 textarea

如果仍然只保留一个编辑框，用户会搞不清：

- 当前编辑的是系统默认还是个人覆盖
- 保存后影响的是自己还是所有人
- 删除后会不会丢失系统默认值

因此前端必须明确区分“系统默认”和“我的覆盖”。

建议严格按以下顺序进行：

### 第一步：补测试规划与文档

### 第二步：数据库落地

- 新增 `PromptTemplate` ORM 模型
- 新增 Alembic 迁移

### 第三步：默认值导入

- 实现从现有文件到数据库的幂等导入逻辑
- 确保系统默认提示词补齐成功

### 第四步：统一服务层

- 新增 `PromptService`

### 第五步：前端页面改造

- 改造提示词管理页
- 加入来源标识、个人覆盖与恢复默认能力

### 第六步：测试与验证

- 后端自动化测试
- 前端手动验证
- 回写进度文档

## 11. 测试规划

## 11.1 后端测试

需要覆盖以下场景：

- 系统默认提示词首次导入成功
- 系统默认提示词缺失时可补齐
- 用户未设置覆盖时返回系统默认
- 用户设置覆盖后优先返回个人内容
- 删除个人覆盖后恢复系统默认
- 不同用户之间的提示词覆盖互不影响
- 普通用户不能修改系统默认
- 管理员可以修改系统默认
- `reading / filter / long` 实际命中的提示词来源正确

## 11.2 前端验证

需要验证以下场景：

- 页面切换类型/步骤自动加载
- 明确显示当前来源
- 保存个人覆盖后刷新仍能命中
- 恢复默认后页面正确回退
- 管理员与普通用户显示不同操作按钮

## 12. 风险与注意事项

### 12.1 风险一：迁移过程中默认值缺失

解决方式：

- 保留文件兜底
- 在导入前后增加完整性校验

### 12.2 风险二：不同分析链路仍各自读取旧逻辑

解决方式：

- 所有业务链路统一改为调用 `PromptService`
- 不允许保留“某模块直接读文件”的旁路

### 12.3 风险三：用户误以为自己在改系统默认

解决方式：

- 前端必须突出显示来源与作用范围
- 系统默认编辑能力仅管理员可见

## 13. 本次推荐结论

本次提示词管理改造，推荐采用以下方案：

- 存储：新增 `prompt_templates` 表
- 组织方式：系统默认 + 用户个人覆盖
- 初始化：从现有文件幂等导入系统默认
- 运行时优先级：个人覆盖 -> 系统默认 -> 文件兜底 -> 代码内置兜底
- 权限：普通用户只能改自己的覆盖，管理员可改系统默认
- 前端：改成可区分来源的提示词中心，而不是单一文本框

这是当前复杂度、可维护性和多用户需求之间最平衡的一套方案。

## 14. 暂不实施的内容

本方案当前只用于规划，不包含实际代码修改。

在用户确认前，暂不执行以下动作：

- 数据库迁移
- 接口改造
- 页面改造
- 提示词导入脚本
- 文档正式回写到进度文档
