## 2. 并发能力评估

### 2.1 优点

| 方面 | 评估 | 说明 |
|------|------|------|
| **任务隔离** | ✅ 良好 | 每个任务在独立线程中运行，互不干扰 |
| **API 响应** | ✅ 良好 | 任务提交后立即返回 `task_id`，不阻塞前端 |
| **状态查询** | ✅ 良好 | 通过轮询 `task_id` 查询进度，支持多任务并行 |

### 2.2 风险点

| 方面 | 风险等级 | 问题描述 |
|------|----------|----------|
| **Uvicorn Workers** | 🟡 中 | `--workers 1` 只有 1 个进程，所有请求共享同一进程 |
| **全局 tasks 字典** | 🟡 中 | 内存中的全局状态，进程重启后丢失 |
| **SQLite 并发** | 🔴 高 | SQLite 是单文件数据库，写操作会锁库 |
| **DeepSeek API 限流** | 🟡 中 | 共用 API Key 可能触发限流 |
| **内存占用** | 🟡 中 | 多个大 PDF 同时处理可能耗尽内存 |
| **磁盘 I/O** | 🟡 中 | 多个任务同时读写文件可能产生竞争 |

## 3. 并发场景模拟

### 场景 1：两个用户同时上传文件精读

```
用户 A (精读 PDF-1)          用户 B (精读 PDF-2)
    │                           │
    ▼                           ▼
POST /reading/quant/start   POST /reading/quant/start
    │                           │
    ▼                           ▼
创建 task_id_A               创建 task_id_B
    │                           │
    ▼                           ▼
Thread A 启动                 Thread B 启动
    │                           │
    ├── 提取 PDF-A              ├── 提取 PDF-B
    ├── 调用 DeepSeek           ├── 调用 DeepSeek  ← 可能触发 API 限流
    ├── 生成报告                ├── 生成报告
    └── 写入数据库              └── 写入数据库      ← SQLite 写锁竞争
```

**可能后果**：

1. **正常情况**：两个任务可以并行执行，因为使用了独立线程
2. **API 限流**：如果两个任务使用相同的 API Key，可能触发 DeepSeek 限流，导致请求失败或变慢
3. **数据库锁**：SQLite 写操作会获取排他锁，两个任务同时写入时会排队等待
4. **内存压力**：两个大 PDF 同时加载到内存，可能增加内存占用

### 场景 2：一个精读 + 一个参考文献梳理

```
用户 A (精读)                 用户 B (参考文献梳理)
    │                           │
    ▼                           ▼
run_quant_task()              run_reference_trace_task()
    │                           │
    ├── 7 步分析                ├── 提取参考文献
    │   ├── Step 1              ├── 调用 DeepSeek
    │   ├── Step 2              ├── 追踪引用
    │   ├── ...                 └── 写入数据库
    │   └── Step 7
    └── 写入数据库
```

**可能后果**：

1. **正常情况**：两个任务可以并行执行
2. **DeepSeek API 并发**：两个任务同时调用 DeepSeek API，如果使用相同 Key，可能触发并发限制
3. **CPU 占用**：PDF 解析是 CPU 密集型操作，两个任务同时运行可能增加 CPU 负载

## 4. 关键瓶颈分析

### 4.1 SQLite 并发限制

```python
# SQLite 写操作示例
await db.execute(insert(Job).values(...))
await db.commit()  # ← 获取排他锁
```

**问题**：
- SQLite 是单文件数据库，写操作会锁住整个数据库
- 多个任务同时写入时，后面的任务会等待前面的完成
- 如果某个任务写入时间过长，其他任务会阻塞

**影响程度**：🟡 中等
- 当前任务量不大时，SQLite 可以处理
- 但如果任务量增加，可能成为瓶颈

### 4.2 DeepSeek API 限流

```python
# 调用 DeepSeek API
client.chat.completions.create(
    model=MODEL,
    messages=messages,
    ...
)
```

**问题**：
- 如果多个用户使用相同的 API Key，可能触发 DeepSeek 的限流策略
- 限流会导致请求失败或响应变慢

**影响程度**：🟡 中等
- 取决于 DeepSeek 的限流策略和用户的 API Key 配置

### 4.3 全局 tasks 字典

```python
# 全局状态
tasks = {}

# 任务创建
tasks[task_id] = init_task_payload(...)

# 任务状态更新
tasks[task_id]["status"] = "running"
tasks[task_id]["progress"] = 50
```

**问题**：
- `tasks` 是内存中的全局字典，进程重启后丢失
- 如果 Uvicorn 重启，所有进行中的任务状态会丢失
- 但任务实际上仍在后台线程运行，只是前端无法查询进度

**影响程度**：🟡 中等
- 当前只有 1 个 worker，重启概率较低
- 但如果需要多 worker 扩展，这个问题会更严重

### 4.4 内存占用

```python
# PDF 加载到内存
paper_text = extractor.extract_content(file_path)

# 大量文本处理
body_text = "\n".join(body_parts)
```

**问题**：
- 大 PDF 文件加载到内存会占用大量空间
- 多个任务同时运行时，内存占用会叠加

**影响程度**：🟡 中等
- 取决于 PDF 文件大小和服务器内存

## 5. 当前系统容量评估

### 5.1 理论并发数

| 资源 | 限制 | 说明 |
|------|------|------|
| Uvicorn Workers | 1 | 所有请求共享同一进程 |
| 线程数 | 无限制 | 每个任务一个线程，但受 CPU 和内存限制 |
| SQLite 连接 | 1 | 单文件数据库，写操作串行 |
| DeepSeek API | 取决于 Key | 不同用户使用不同 Key，限流独立 |

### 5.2 实际建议并发数

| 场景 | 建议并发数 | 说明 |
|------|------------|------|
| 轻量操作（查询、上传） | 10+ | 可以轻松处理 |
| 精读任务 | 2-3 | 受 DeepSeek API 和内存限制 |
| 参考文献梳理 | 2-3 | 受 DeepSeek API 和 PDF 解析限制 |
| 混合场景 | 3-5 | 精读 + 梳理 + 查询同时进行 |

## 6. 风险场景与后果

### 6.1 低风险场景

**场景**：两个用户同时查询文献列表
**后果**：✅ 无影响，读操作不冲突

### 6.2 中风险场景

**场景**：两个用户同时开始精读
**后果**：
- ✅ 任务可以并行执行
- ⚠️ 如果使用相同 API Key，可能触发 DeepSeek 限流
- ⚠️ 数据库写入会排队，但通常很快

### 6.3 高风险场景

**场景**：3+ 用户同时进行重度任务（精读 + 梳理 + 筛选）
**后果**：
- ⚠️ 内存占用可能激增
- ⚠️ DeepSeek API 可能频繁限流
- ⚠️ 数据库写入可能阻塞
- ❌ 极端情况下可能导致任务超时或失败

## 7. 改进建议

### 7.1 短期优化（低成本）

| 优化项 | 实施难度 | 效果 |
|--------|----------|------|
| 增加 Uvicorn workers | 🟢 低 | 提高 API 响应能力 |
| 添加任务队列 | 🟡 中 | 控制并发任务数量 |
| SQLite WAL 模式 | 🟢 低 | 提高并发读写能力 |
| 任务超时机制 | 🟢 低 | 防止任务长时间占用资源 |

### 7.2 中期优化（中等成本）

| 优化项 | 实施难度 | 效果 |
|--------|----------|------|
| 使用 Redis 存储任务状态 | 🟡 中 | 支持多 worker，状态持久化 |
| 连接池管理 | 🟡 中 | 提高数据库并发能力 |
| API Key 轮换 | 🟡 中 | 避免单个 Key 限流 |
| 内存限制和监控 | 🟡 中 | 防止内存溢出 |

### 7.3 长期优化（高成本）

| 优化项 | 实施难度 | 效果 |
|--------|----------|------|
| 迁移到 PostgreSQL | 🔴 高 | 彻底解决 SQLite 并发限制 |
| 分布式任务队列（Celery） | 🔴 高 | 支持大规模并发 |
| 微服务架构 | 🔴 高 | 完全解耦各模块 |

## 8. 立即可执行的优化

### 8.1 启用 SQLite WAL 模式

```python
# 在数据库连接时添加
import sqlite3

conn = sqlite3.connect('db/app.sqlite')
conn.execute('PRAGMA journal_mode=WAL')
conn.execute('PRAGMA synchronous=NORMAL')
```

### 8.2 增加 Uvicorn Workers

```bash
# 修改 start.sh
uvicorn main:app --host 0.0.0.0 --port 8000 --workers 2
```

**注意**：增加 workers 后，全局 `tasks` 字典不能跨 worker 共享，需要改用 Redis 或数据库存储任务状态。

### 8.3 添加任务数量限制

```python
# 在路由中添加并发任务检查
MAX_CONCURRENT_TASKS = 5

async def start_reading(...):
    running_count = sum(1 for t in tasks.values() if t.get("status") == "running")
    if running_count >= MAX_CONCURRENT_TASKS:
        raise HTTPException(429, "系统繁忙，请稍后再试")
```

## 9. 总结

### 当前并发能力评级

| 维度 | 评级 | 说明 |
|------|------|------|
| **轻量操作** | ✅ 优秀 | 查询、上传等操作可以轻松处理并发 |
| **单任务** | ✅ 良好 | 单个精读/梳理任务可以稳定运行 |
| **双任务并发** | 🟡 一般 | 可以并行，但可能受 API 限流影响 |
| **多任务并发** | ⚠️ 风险 | 3+ 任务同时运行可能出现性能问题 |

### 结论

**当前系统可以支持 2-3 个用户同时使用**，但需要注意：

1. **API Key 配置**：建议不同用户使用不同的 DeepSeek API Key，避免限流
2. **任务监控**：关注服务器内存和 CPU 使用情况
3. **数据库优化**：启用 SQLite WAL 模式提高并发能力
4. **任务限制**：添加并发任务数量限制，防止系统过载

如果用户量增长到 5+ 并发用户，建议考虑：
- 增加 Uvicorn workers（需要解决 tasks 状态共享问题）
- 迁移到 PostgreSQL
- 使用 Redis 作为任务队列
