# PDF 元数据在线匹配规划

## 1. 背景

当前系统已经具备一层基础匹配能力：

- 用户上传 PDF 后，后端会尝试用文件名标题去匹配当前用户已有的 `bib_entries`。
- 如果上传阶段没有命中，开始精读时还会再做一轮基于标题的兜底匹配。

这套能力已经能覆盖一部分场景，但仍有明显局限：

- 文件名不规范时，标题匹配会失效。
- 文件名里常混有作者名、年份、下载站后缀、下划线、空格噪音。
- 有些 PDF 首页没有完整期刊名，期刊名可能出现在第二页或第三页页眉。
- 仅靠本地标题相似度，无法补全缺失的 DOI、作者、期刊、卷期页码等元数据。

因此，需要引入更接近 Zotero 的“多阶段识别 + 在线候选检索 + 置信度评分 + 必要时人工确认”的能力。

## 2. 目标

本次规划的目标不是单纯“再做一次标题搜索”，而是构建一条更稳的 PDF 元数据匹配链路：

1. 先匹配当前用户数据库里已经存在的题录。
2. 如果本地库没有命中，则从 PDF 前 1-3 页提取高价值文本线索。
3. 必要时调用 `DeepSeek` 从这些文本中抽取结构化元数据。
4. 基于结构化线索做在线候选检索与排序。
5. 对高置信度候选自动应用，对中等置信度候选交给用户确认。

## 3. 对标 Zotero 的核心思路

Zotero 的自动识别能力，本质上不是“拿文件名搜一下”，而是分层处理：

1. 先从 PDF 自身找强标识符：
   - DOI
   - ISBN
   - arXiv ID
   - PMID
   - PDF 内嵌元数据
2. 再抽正文线索：
   - 标题
   - 作者
   - 年份
   - 期刊名
   - 摘要前几行
3. 再去外部数据源查候选。
4. 对候选做打分。
5. 置信度不足时，让用户确认。

本项目不需要机械照搬 Zotero 的所有数据源，但应学习这种“分阶段证据融合”的方法。

## 4. 本项目推荐方案

### 4.1 总体链路

推荐按以下顺序执行：

1. **本地题录匹配**
   - 在当前用户自己的 `bib_entries` 中查找可能匹配项。
   - 这是最快、最稳定的一层。

2. **PDF 线索提取**
   - 提取文件名标题。
   - 提取 PDF 第 1 页全文。
   - 如果第 1 页没有足够信息，再补提第 2 页和第 3 页的页眉/前几段文本。

3. **结构化元数据抽取**
   - 优先做规则提取：
     - DOI 正则
     - 年份
     - 常见作者行
     - 常见期刊格式
   - 如果规则提取不足，再调用 `DeepSeek` 从前 1-3 页文本中抽取：
     - 标题
     - 作者
     - 年份
     - 期刊名
     - DOI
     - 语言
     - 文献类型线索

4. **在线候选检索**
   - 英文文献优先查公开 API。
   - 中文文献优先评估可用的中文来源。
   - 目标是拿到若干候选元数据，而不是只返回一条。

5. **候选打分**
   - 标题相似度
   - 作者重合度
   - 年份差异
   - 期刊名相似度
   - DOI 是否完全一致
   - PDF 提取语言与候选来源是否一致

6. **应用策略**
   - 高置信度：自动绑定或自动补全空字段
   - 中等置信度：展示候选让用户确认
   - 低置信度：不自动应用，仅提示手动处理

### 4.2 为什么要读取前 1-3 页

仅取文件名远远不够，仅取首页也不一定足够。

实际论文中常见情况：

- 标题与作者在第一页。
- DOI 可能在第一页页脚。
- 期刊名、卷期页码、出版信息可能在第二页或第三页页眉。
- 中文社科论文中，第一页有时信息不规整，第二页反而更容易看出刊物来源。

因此，本项目建议：

- 默认抽取第一页全文。
- 同时抽取第二页、第三页的页眉和开头若干行。
- 将这三页组合成“元数据识别上下文”，而不是把整篇论文都送去做在线匹配。

这样可以兼顾：

- 识别精度
- 成本控制
- 响应速度

## 5. DeepSeek 的使用方式

### 5.1 角色定位

`DeepSeek` 在这条链路中不直接替代数据库匹配和在线检索，而是承担“从有限文本中提取结构化线索”的工作。

推荐定位：

- **抽取器**，不是最终裁判
- 输出候选线索，不直接决定最终落库结果

### 5.2 输入建议

输入给 `DeepSeek` 的内容包括：

- 文件名
- PDF 第 1 页全文
- PDF 第 2 页页眉 + 前若干行
- PDF 第 3 页页眉 + 前若干行

### 5.3 输出建议

要求 `DeepSeek` 以结构化 JSON 输出：

- `title`
- `authors`
- `year`
- `journal`
- `doi`
- `language`
- `document_type`
- `confidence`
- `notes`

### 5.4 使用原则

- 如果规则提取已经拿到明确 DOI，则不必强依赖模型判断标题。
- 如果模型输出缺少关键信息，不直接落库。
- 模型结果用于“生成搜索线索”和“候选打分增强”，不直接覆盖已有高质量人工题录。

## 6. 在线检索源规划

### 6.1 英文文献

推荐优先级：

1. DOI 直接查询
2. Crossref
3. OpenAlex
4. Semantic Scholar（可选）

不建议把 `Google Scholar` 作为主路径，原因：

- 没有稳定官方 API
- 反爬严格
- 自动化长期稳定性差

如果后续确有必要，可以把 `Google Scholar` 放在：

- 人工触发的增强检索
- 低频补充通道

而不是基础设施主链路。

### 6.2 中文文献

中文文献推荐优先级：

1. 先用本地题录匹配
2. 如果 PDF 文本中已提取到 DOI，则优先用 DOI 反查
3. 再评估 `CNKI` 自动化是否可用
4. 必要时增加人工确认步骤

需要注意：

- `CNKI` 对用户体验很重要，但自动化稳定性与可维护性需要单独验证。
- 中文社科论文很多没有 DOI，因此标题、作者、刊名三元组的重要性会更高。

### 6.3 当前建议

先把在线匹配系统设计成“多数据源可插拔”：

- `LocalBibSource`
- `DoiLookupSource`
- `CrossrefSource`
- `OpenAlexSource`
- `CnkiSource`（待可行性验证）

这样后续即使某个来源不可用，也不会拖垮整体能力。

## 7. 匹配评分策略

建议统一产出一个 `match_score`，范围 `0.0 - 1.0`。

打分因子建议：

- DOI 完全一致：最高权重
- 标题相似度：高权重
- 作者首作者匹配：高权重
- 作者集合重合度：中高权重
- 年份一致：中权重
- 期刊名匹配：中权重
- 语言一致：中低权重
- 文献类型一致：中低权重

推荐分档：

- `>= 0.92`：高置信度，可自动绑定
- `0.78 - 0.92`：中等置信度，建议前端确认
- `< 0.78`：不自动应用

注意：

- 如果 DOI 完全一致，即使标题格式有轻微差异，也应优先认定为高置信度。
- 如果没有 DOI，则不能只靠模糊标题就直接强行覆盖已有数据。

## 8. 前端产品形态规划

### 8.1 “我的文献库”入口

在“我的文献库”中为单篇文献增加：

- `在线匹配`
- `查看候选`
- `应用推荐`
- `手动选择`

同时展示元数据状态，例如：

- 已完整
- 缺 DOI
- 缺作者
- 缺期刊
- 未在线校验

### 8.2 PDF 上传后反馈

在 PDF 上传响应中，除了当前已有的本地匹配信息，还可以补充：

- 是否已尝试在线匹配
- 是否提取到 DOI
- 是否拿到推荐候选
- 是否需要人工确认

### 8.3 批量补全入口

建议后续为管理员或当前用户提供：

- 扫描缺失元数据文献
- 批量在线补全
- 仅自动应用高置信度结果

## 9. 后端设计建议

### 9.1 服务拆分

建议新增以下服务层：

- `pdf_metadata_extract_service`
  - 从 PDF 提取前 1-3 页文本线索
- `pdf_metadata_llm_service`
  - 调用 `DeepSeek` 输出结构化线索
- `metadata_match_service`
  - 聚合本地库、DOI、在线来源候选并打分
- `metadata_apply_service`
  - 控制如何把候选结果应用到 `bib_entries`

### 9.2 接口建议

先规划，不立即全部实现。建议接口如下：

#### `POST /api/library/entries/{entry_id}/match-online`

作用：

- 针对单条文献执行在线匹配
- 返回候选列表、推荐项、匹配分数

#### `POST /api/library/entries/{entry_id}/apply-match`

作用：

- 应用用户选中的候选元数据

#### `POST /api/library/files/{file_id}/match-online`

作用：

- 针对 PDF 文件直接做在线匹配
- 如果命中题录，则同步更新或绑定 `bib_entries`

#### `POST /api/library/match-missing`

作用：

- 批量扫描当前用户缺失元数据的文献并给出候选

## 10. 数据更新原则

元数据更新必须保守，避免误覆盖。

建议支持两种模式：

### 10.1 只补空字段

默认模式：

- 如果当前 `bib_entries` 已有标题、作者、年份，则不覆盖
- 只补 DOI、期刊、卷期页码、摘要等缺失项

### 10.2 人工确认后整条覆盖

仅在用户明确确认时允许：

- 用在线候选整体替换现有元数据

## 11. 风险与注意点

### 11.1 识别风险

- PDF OCR 或文本提取质量不稳定
- 首页标题可能被错误分段
- 页眉页脚可能引入噪音

### 11.2 数据源风险

- `Google Scholar` 不适合作为唯一主源
- `CNKI` 自动化能力需要单独验证稳定性
- 某些来源可能有访问频率限制

### 11.3 覆盖风险

- 错误候选一旦自动覆盖，会污染后续精读、对比、综述链路
- 因此必须优先采用“只补空字段 + 中置信度人工确认”

## 12. 分阶段实施建议

### 第一阶段：增强识别，不接外部站点

目标：

- 保留当前本地题录匹配
- 增加 PDF 前 1-3 页文本抽取
- 增加 DOI/标题/作者/年份规则识别
- 增加 `DeepSeek` 结构化线索提取

这一阶段的价值：

- 即使不接外部站点，也能显著提高匹配线索质量

### 第二阶段：接入英文公开数据源

目标：

- DOI 查询
- Crossref
- OpenAlex
- 候选打分和高置信度自动补全

### 第三阶段：接入中文在线增强源

目标：

- 评估 `CNKI` 自动化可行性
- 如可行，再接入候选检索
- 如不可行，则提供人工辅助确认流程

### 第四阶段：前端批量工具

目标：

- 文献库里可见元数据缺失状态
- 支持单篇在线匹配
- 支持批量扫描与批量补全

## 13. 当前建议结论

当前最合理的方向是：

1. 保留现有“本地题录自动匹配”能力
2. 增加“读取 PDF 前 1-3 页文本”的识别链路
3. 调用 `DeepSeek` 做结构化线索抽取
4. 用结构化线索去做在线候选搜索
5. 用候选评分和人工确认控制风险

这条路线既保留了当前系统已经可用的基础匹配，又能逐步接近 Zotero 风格的自动识别体验。

本文档仅用于规划，不代表当前功能已经实现。

当前阶段：
