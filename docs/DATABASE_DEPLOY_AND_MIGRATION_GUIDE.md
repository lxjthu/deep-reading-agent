# 数据库设计、迁移与部署说明

> 适用项目：`deep-reading-agent`  
> 适用场景：本机持续开发、通过 GitHub 自动部署到服务器、服务器使用 SQLite + Alembic 管理数据库结构

## 1. 这份文档解决什么问题

这份文档专门回答下面几个容易混淆的问题：

- 本机改了数据库设计，服务器如何知道这些改动？
- 推代码到 GitHub 后，服务器自动部署时，数据库会不会自动更新？
- 数据库结构变了以后，要不要把本机的数据库文件重新传到服务器？
- `docs/DATABASE_SCHEMA.md`、`backend/db/models.py`、`backend/migrations/versions/*.py` 各自是什么关系？
- 本机数据库和服务器数据库是否需要同步？

如果你后续继续推进数据库相关开发，建议把这份文档当作数据库上线流程的统一说明。

---

## 2. 当前项目的真实部署链路

当前项目的代码部署链路是：

1. 在本机修改代码
2. 提交并推送到 GitHub
3. 服务器自动拉取最新代码并重启服务

但是，**数据库结构变更不等于代码自动部署**。

也就是说：

- GitHub 自动部署会让服务器拿到新的代码
- 但服务器上的 `db/app.sqlite` 不会因为“代码变了”就自动修改表结构
- 数据库结构是否改变，取决于你是否执行了 Alembic 迁移

因此，当前项目的完整上线逻辑应该理解为：

1. 推送代码到 GitHub
2. 服务器自动部署代码
3. 服务器手动执行数据库迁移
4. 验证服务是否正常

---

## 3. 数据库设计变更，服务器到底靠什么“知道”

服务器不会读取设计文档来改数据库。

服务器真正能“知道”数据库结构变化，只能通过下面两类仓库内容：

### 3.1 ORM / 模型代码

也就是：

- `backend/db/models.py`

作用：

- 告诉应用程序“现在代码认为数据库应该长什么样”
- 用于 ORM 查询、插入、更新、关联关系映射

但是请注意：

- **只改 `models.py`，不会自动修改服务器数据库**

---

### 3.2 Alembic 迁移脚本

也就是：

- `backend/migrations/versions/*.py`

作用：

- 告诉 Alembic：从旧结构到新结构应该怎么改
- 例如：新增表、增加字段、改约束、补索引、调整枚举范围

只有迁移脚本才是数据库结构真正变化的“执行说明”。

因此，服务器“知道数据库怎么改”的根本来源是：

- 你推上去的 Alembic 迁移文件

---

## 4. 设计文档、模型、迁移、数据库四者的关系

可以把它们理解成四层：

### 4.1 设计层

文件：

- `docs/DATABASE_SCHEMA.md`

作用：

- 记录数据库应该如何设计
- 描述表、字段、关系、约束、用途、生命周期

特点：

- 给人看
- 不会直接改变数据库

---

### 4.2 代码层

文件：

- `backend/db/models.py`

作用：

- 把设计层落到 SQLAlchemy ORM 模型
- 让后端代码按新的数据库结构运行

特点：

- 给程序运行时使用
- 不会直接修改已存在的数据库文件

---

### 4.3 迁移层

文件：

- `backend/migrations/versions/*.py`

作用：

- 把“旧数据库”一步一步变成“新数据库”
- 是数据库结构变化的正式执行路径

特点：

- 给 Alembic 执行
- 这是数据库上线的核心

---

### 4.4 运行层

文件：

- `db/app.sqlite`

作用：

- 真正在线运行的数据文件

特点：

- 会保存真实用户数据、任务记录、文献条目、产物关系等
- 不应该被本机测试库直接覆盖

---

### 4.5 一句话概括

四者关系如下：

- `DATABASE_SCHEMA.md` 负责“说明应该怎么设计”
- `models.py` 负责“告诉代码现在按什么结构运行”
- `migrations/*.py` 负责“告诉数据库该怎么从旧版升级到新版”
- `db/app.sqlite` 是“最终被升级并被服务使用的真实数据库”

---

## 5. 为什么不能只改文档或只改模型

很多数据库问题都来自“只改了一部分”。

### 5.1 只改文档，不改模型和迁移

结果：

- 设计文档是新的
- 实际代码还是旧结构
- 数据库也是旧结构

这会导致“文档正确，系统不工作”。

---

### 5.2 只改模型，不写迁移

结果：

- 应用代码按新结构访问数据库
- 但服务器数据库还是旧表结构

常见后果：

- 启动时报错
- 查询时报错
- 插入时报错
- ORM 字段和数据库字段不一致

---

### 5.3 只写迁移，不改模型

结果：

- 数据库已经升级了
- 但代码还在按旧结构读写

这会导致：

- 新字段用不上
- 新关系无代码支持
- 新表存在但没有业务入口

---

### 5.4 正确做法

数据库设计改动要同时完成三件事：

1. 更新设计文档
2. 更新 `models.py`
3. 新增或调整 Alembic 迁移

上线后再执行：

4. 服务器运行 `alembic upgrade head`

---

## 6. 为什么通常不需要把本机数据库传到服务器

对于当前项目，**正常情况下不应该把本机数据库文件上传覆盖服务器数据库**。

原因如下：

### 6.1 本机数据库和服务器数据库职责不同

- 本机数据库：开发、测试、看效果
- 服务器数据库：真实运行数据

它们本来就不应该强行同步。

---

### 6.2 上传本机数据库会覆盖服务器现有数据

如果你直接把本机 `db/app.sqlite` 上传到服务器替换线上库，可能会导致：

- 服务器已有数据丢失
- 用户数据丢失
- 任务记录丢失
- 线上状态被本机测试状态覆盖

---

### 6.3 正确思路不是“传数据库”，而是“传迁移规则”

服务器不需要本机数据库文件。

服务器需要的是：

- 新代码
- 新模型
- 新迁移脚本

然后在服务器自己的数据库上执行迁移。

换句话说：

- 不是把本机数据库拷过去
- 而是让服务器数据库**按同样的规则升级**

---

## 7. 当前项目最推荐的数据库上线方式

结合当前项目现状，推荐始终使用下面这套流程。

### 7.1 本机开发阶段

在本机完成：

- 设计文档更新
- `backend/db/models.py` 更新
- `backend/migrations/versions/` 新迁移脚本
- 后端逻辑适配
- 前端逻辑适配
- 本机测试验证

---

### 7.2 提交与推送阶段

把下面内容一起提交到 Git：

- 代码改动
- `models.py`
- Alembic 迁移文件
- 必要时的测试文件
- 必要时的说明文档

然后推送到 GitHub。

---

### 7.3 服务器自动部署阶段

服务器自动部署后会发生：

- 拉取最新代码
- 重启服务

但此时数据库一般仍然是旧结构，除非你已经额外做了自动迁移逻辑。

当前项目不建议依赖自动迁移脚本直接改数据库，而是继续手动执行迁移更稳妥。

---

### 7.4 服务器手动迁移阶段

SSH 登录服务器后，执行：

```bash
cd /root/.openclaw/workspace/deep-reading-agent/backend
source ../venv/bin/activate
python -m alembic upgrade head
```

这一步的意义是：

- 让服务器当前数据库结构追上最新代码需要的结构

---

### 7.5 服务器验证阶段

迁移完成后，再检查：

- 服务是否能正常启动
- 页面是否可访问
- 新功能接口是否正常
- 新表是否已创建
- 老数据是否未被破坏

---

## 8. 当前项目为什么更要重视迁移链

当前项目有一个非常重要的现实情况：

- 本机已经有大量修改，但尚未推送
- 服务器代码和数据库阶段落后于本机

这会带来一个直接影响：

- 服务器上线时不能假设“只跑最后一个迁移就够了”

而应该按真实迁移链来处理。

例如，如果服务器当前停在较早版本，而本机已经新增了多轮数据库改动，那么服务器上线后应该让 Alembic 按顺序补齐中间迁移，而不是跳过。

因此本项目未来任何数据库改动都应坚持：

- 每次结构变化都写独立迁移
- 不依赖“手改 sqlite 文件”
- 不依赖“本机数据库替换线上数据库”

---

## 9. 什么时候才需要手动传数据库文件

只有下面这些特殊场景，才可能考虑手动传数据库文件：

### 9.1 初始化一个全新的空服务器

例如：

- 服务器还没有任何数据库
- 你只是临时想快速拷一份测试数据过去

即便如此，正式环境也更建议：

- 先建空库
- 再通过迁移和脚本初始化

---

### 9.2 做离线备份或恢复

例如：

- 备份线上数据库
- 故障恢复时恢复某个备份版本

这属于运维操作，不属于正常开发上线流程。

---

### 9.3 明确决定用某份数据库完全覆盖另一份

这是非常危险的操作，必须明确确认后才做。

对于当前项目的正常开发流程，这不是推荐方案。

---

## 10. 本机、GitHub、服务器、数据库之间的推荐关系

建议把当前项目理解为下面的关系：

### 10.1 本机

负责：

- 开发
- 测试
- 修改文档
- 修改模型
- 编写迁移

---

### 10.2 GitHub

负责：

- 承载代码版本
- 作为服务器自动部署的代码来源

---

### 10.3 服务器

负责：

- 拉取代码
- 重启服务
- 执行数据库迁移
- 承载真实业务数据

---

### 10.4 服务器数据库

负责：

- 保存线上真实数据
- 通过 Alembic 升级结构
- 不直接用本机数据库覆盖

## 11. 推荐的标准操作清单

以后只要涉及数据库设计变更，建议按下面清单执行：

### 阶段 A：本机开发

1. 更新 `docs/DATABASE_SCHEMA.md`
2. 更新 `backend/db/models.py`
3. 新增 Alembic 迁移文件
4. 更新业务代码
5. 更新测试
6. 在本机数据库验证迁移和功能

### 阶段 B：提交代码

1. 检查迁移文件是否已纳入提交
2. 检查模型和迁移是否一致
3. 检查本机功能已验证
4. 提交到 Git
5. 推送到 GitHub

### 阶段 C：服务器上线

1. 等服务器自动部署完成
2. SSH 登录服务器
3. 进入项目目录并激活 `venv`
4. 执行 `python -m alembic upgrade head`
5. 检查服务是否正常
6. 检查页面和功能是否正常

## 12. 常见误区

### 误区 1：改了 `DATABASE_SCHEMA.md`，服务器就会知道

错误。

原因：

- 文档不会自动改数据库

---

### 误区 2：改了 `models.py`，服务器数据库就会自动变化

错误。

原因：

- ORM 模型不会自动修改已有库表结构

---

### 误区 3：推到 GitHub 自动部署后，数据库也会自动完成升级

当前项目下不成立。

原因：

- 服务器自动部署的是代码，不是数据库迁移执行本身

---

### 误区 4：数据库设计变了，就应该把本机数据库上传到服务器

错误。

原因：

- 这样容易覆盖服务器真实数据
- 正确做法是让服务器按迁移脚本升级自己的数据库

---

## 13. 当前项目的建议结论

基于当前项目状态，建议始终坚持下面原则：

- 本机数据库和服务器数据库分开使用
- 数据库设计改动必须同步到 `models.py` 和 Alembic 迁移
- GitHub 自动部署后，不要默认数据库已更新
- 服务器继续手动执行 `alembic upgrade head`
- 不要用本机数据库直接覆盖服务器数据库

---

## 14. 与当前 P0 任务的对齐说明

当前待实施的 `P0` 是：

- `参考文献梳理标签页 + 引用关系入库`

这个任务不是单纯新增一个前端标签页，而是会同时涉及下面几层变化：

### 14.1 数据库层

可能新增或调整以下类型的数据结构：

- 源 PDF 的参考文献梳理任务记录
- 参考文献条目与源文件的关联关系
- 正文中的引用片段入库
- 源文献与被引文献之间的关系表
- 梳理结果产物或任务状态表扩展

这部分必须通过：

- `backend/db/models.py`
- `backend/migrations/versions/*.py`

来正式落地。

---

### 14.2 后端能力层

`P0` 至少会包含下面几个最小闭环能力：

- 选择一篇已入库 PDF
- 提取该 PDF 的参考文献目录
- 结构化参考文献条目
- 提取正文中的引用片段
- 建立引用片段与参考文献条目的对齐结果
- 把结果保存到数据库
- 向前端返回可展示的表格数据

因此，数据库结构设计不能只满足“存条目”，还要满足：

- 存来源文件
- 存引用文本
- 存匹配状态
- 存源文献到被引文献的关系

---

### 14.3 部署层

本次 `P0` 如果落地，服务器上线时应遵循下面顺序：

1. 推送包含 `P0` 代码和迁移文件的提交到 GitHub
2. 等服务器自动部署并重启代码
3. SSH 登录服务器
4. 激活项目 `venv`
5. 手动执行 `python -m alembic upgrade head`
6. 使用服务器现有数据库继续运行，不上传本机数据库文件
7. 用服务器现有 PDF 数据验证参考文献梳理功能

这一步尤其重要：

- **服务器需要执行迁移，不需要替换数据库文件**

---

### 14.4 本机验证层

本次 `P0` 在本机验证时，推荐优先使用：

- 当前本机数据库里已经存在的 PDF 数据

这样做的好处是：

- 可以直接验证“已有文档是否能跑通梳理流程”
- 可以提前看到入库结果和表格效果
- 可以更早暴露引用对齐、参考文献解析、任务状态落库中的问题

---

### 14.5 当前任务执行原则

针对这次 `P0`，后续开发应坚持下面原则：

- 先按 `DATABASE_SCHEMA.md` 设计数据库改动
- 再落到 `models.py`
- 再补 Alembic 迁移
- 再接后端任务闭环
- 再接前端展示
- 先在本机现有 PDF 数据上验证
- 等功能和效果确认后，再统一更新核心文档

这也是当前 `P0` 最稳妥的推进顺序。

---

## 15. 一句话总结

**服务器不是通过“接收你的数据库文件”知道数据库改动的，而是通过“你推上去的模型代码 + 迁移脚本”，并在执行 Alembic 迁移后，才真正完成数据库结构升级。**
